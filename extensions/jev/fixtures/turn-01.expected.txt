**Why this spec exists.** Two live conditions the existing tests and instrumentation do not cover:

1. `DRY_RUN` is now `'false'` and `RECIPIENT_EMAIL` holds the client address. Mail suppression in the suite is per-test: each test that can reach `send` / `alert` opts in by wrapping itself in `_withNoMail_`. That is a convention. One test added without the wrapper mails the client from a test run. The blast radius changed on 2026-09-07; the mechanism did not.
2. Three `collect` executions timed out. `appendPool_` and `writeHealth_` are both at the end of the `try`, and a hard execution timeout is not an exception — the `catch` never runs. A timed-out collect therefore appends nothing, writes no health row, and is indistinguishable on the `health` tab from a trigger that never fired and from a `collect skipped: lock held` return.

## 1. `src/Test.gs` — suite-level mail guard

### 1.1 The problem

`_withNoMail_` is applied by four tests: `test_run`, `test_invariant_run_never_throws`, `test_invariant_zero_items_alerts_no_email`, `test_invariant_collect_never_throws`. That is currently complete coverage of the tests that can reach `send` / `alert`. It is complete by inspection, not by construction. The failure mode is a future test — or a future code path inside an existing test — that reaches `send()` with `DRY_RUN === 'false'`, which mails `RECIPIENT_EMAIL`.

The gotcha card already records that `test_all` mailed the operator once. That regression was closed by making `alert()` honour `DRY_RUN`. `DRY_RUN` is no longer `'true'`, so that protection is inert.

### 1.2 The fix

Install the stubs once, around the test loop, and restore in a `finally`. Rebinding a top-level function on the global object rebinds it for every `.gs` file in the execution — that is exactly the property being relied on, and it is the same mechanism `_withNoMail_` already uses.
