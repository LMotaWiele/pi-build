## The alternative

The idiomatic alternative is to always produce a walkthrough after every edit turn. This change instead asks the explain model whether the edit introduced unfamiliar surface and writes only when the response indicates it did. That avoids cluttering `.agent/explain/` with explanations the reader doesn’t need.

## Verify by hand

- Confirm the configured reader profile describes the intended audience and that a host without a custom profile still has sensible behavior.
- Try an edit introducing a genuinely unfamiliar API and one using only known concepts; check that only the first creates a walkthrough.
- Check that a failed explain call or aborted run does not create a walkthrough or update the known list.

## To modify this yourself

First understand the explain lifecycle: telemetry captures tool edits, the `agent_end` handler snapshots them, and `lib/explain.ts` builds and parses the learning-aid response. Then review how host settings choose the explain model and how the pipeline flag reaches child processes before changing routing or pipeline behavior.
