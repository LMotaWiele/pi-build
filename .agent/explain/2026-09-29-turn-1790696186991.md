## What changed

- `lib/telemetry.ts` removes loop-depth, wall-clock, failure-count, and no-progress limits from `BoundConfig`; prompt-token and cost budgets remain.
- `extensions/bounds.ts` adds stuck-work detection and escalation, tracks compaction state, and automatically continues after eligible compactions; retry attempts now return the selected model or `null`.
- `agent/EXTENSIONS.md` documents the updated bounds event responsibilities and quota-gate behavior.

## Unfamiliar surface

The diff introduces these APIs and patterns not in `known.md`:

- `pi.sendMessage(..., { deliverAs: "steer" })` sends the first stuck-work nudge as steering input during the current turn.
- `pi.sendUserMessage(..., { deliverAs: "followUp" })` queues a “continue” message to start another turn after compaction.
- `event.messages?.some(...)` checks whether any ended-turn message contains the compaction recovery failure marker; `Boolean(...)` normalizes the result to a boolean.
- `event.content ?? []` and `.map(...).join("\n")` safely collect text from tool-result content parts.
- `process.cwd()` obtains the current working directory; `fs.readFileSync(path, "utf8")` reads the optional resume note synchronously.
- `async` callbacks and `Promise<string | null>` represent an awaited retry that either selects a model name or has no target.
- `type`-only imports bring in TypeScript types without runtime imports.
- `pi.appendEntry(...)` stores custom session entries for findings and headless continuation requests.
- `event.isError`, tool names, and edit/write tool-result fields drive error tracking and reset the no-edit continuation streak.
- The compaction hooks `session_before_compact` and `agent_end` capture compaction state and decide whether to continue, stop, or escalate.
- `ctx.mode` distinguishes print and JSON modes from interactive mode, where sending a follow-up is possible.
- `String.startsWith(...)` checks whether a prompt is the automatic `"continue"` prompt so that its overflow streak is preserved.
- `null` as a return value explicitly indicates “no retry target,” replacing the old implicit `undefined`.

## The alternative

The earlier bounds model used fixed loop, time, failure, and no-progress thresholds. This change relies on pattern-based stuck detection and compaction recovery instead, with token and cost budgets still guarding resource use. For stuck work, the alternative is to stop immediately or retry on every finding; this implementation nudges once, then escalates only on a subsequent finding and only when retry policy and quota-hold checks allow it. For compaction, the alternative is to leave recovery to the user; this change continues automatically when eligible, while recording a continuation-needed entry in print/JSON modes.

## Verify by hand

- Confirm a first stuck finding sends one steering nudge and a later finding escalates or stops as intended, including when quota hold or retry settings block escalation.
- Confirm compaction recovery failure and repeated no-edit continuations lead to escalation, while a successful edit resets the continuation streak.
- Check print and JSON modes record `pi-build-continue-needed` rather than attempting an interactive follow-up.

## To modify this yourself

Start with `extensions/bounds.ts` and trace how `detectStuck`, `continueAfterCompaction`, and the retry/abort helpers coordinate. Then review `lib/telemetry.ts` for the remaining budget configuration and `agent/EXTENSIONS.md` for the event-order contract. Keep per-turn state resets aligned with turn IDs, and preserve the distinction between interactive follow-ups and headless session records.
